# free list 메모리 할당기

## 한 줄 요약

빈 메모리 조각들을 **목록(free list)** 으로 들고 있다가, 요청이 오면 맞는 조각을 떼어 주고, 반납되면 다시
목록에 넣는 것. `malloc`, 커널 slab, vLLM의 KV 블록 풀, GPU 메모리 캐싱 할당기가 모두 이 위에 있다.
System SW 면접에서 링 버퍼, LRU와 함께 "직접 짜 보라"고 가장 자주 나오는 셋 중 하나다.

## 두 종류

| | 크기 제각각 (예제 1 `first_fit`) | 크기 하나 (예제 2 `block_pool`) |
|---|---|---|
| 목록에 든 것 | (시작 주소, 크기) 조각 | 같은 크기 블록 |
| 할당 | 맞는 조각 찾기 O(조각 수) + 남는 부분 떼기(split) | 머리에서 하나 빼기 O(1) |
| 반납 | 주소 순 자리에 넣고 양옆과 합치기(coalescing) | 머리에 넣기 O(1) |
| 문제 | **외부 단편화**: 빈 칸 합계는 충분한데 연속으로는 모자람 | 내부 단편화(요청보다 블록이 크면 남는 부분) |
| 쓰는 곳 | malloc, 큰 텐서 할당 | KV 블록, 커널 slab, 객체 풀 |

## 예제 1: first-fit + 분할 + 병합

16칸에 a·b·c를 4칸씩 → 0, 4, 8. b를 반납한 뒤 6칸을 요청하면 **빈 칸은 8칸(4~7, 12~15)인데 연속 6칸이 없어서
실패(-1)** — 외부 단편화. a까지 반납하면 0~3과 4~7이 합쳐져 0~7이 되고, 다시 요청한 6칸이 0에 들어간다.
마지막에 남은 칸 7, 가장 큰 연속 빈 칸 6.

검증: 무작위 300개 명령열에서, 칸 하나하나에 주인을 적는 단순 배열 모델(크기만큼 연속으로 빈 가장 낮은 주소)과
**매 연산의 주소, 빈 칸 합계, 가장 큰 연속 빈 칸**을 비교했고 Python과 C++ 출력도 같았다. 병합을 빠뜨리면 "가장 큰
연속 빈 칸"이 모델과 달라져 바로 걸린다. (병합이 완전하면 빈 조각이 늘 최대 구간이므로 first-fit 주소가 배열
모델의 "가장 낮은 연속 구간"과 같아진다. 이게 두 구현을 비교할 수 있는 이유다.)

## 예제 2: 같은 크기 블록 풀 (intrusive free list)

빈 블록 **안쪽 첫 8바이트에 다음 빈 블록 주소를 적어 둔다**. 빈 블록은 어차피 아무도 안 쓰므로 목록을 위한
메모리가 따로 필요 없다. 할당은 `head = head->next`, 반납은 `p->next = head; head = p`.
반납한 블록이 바로 다음 할당에 나가므로(LIFO) 캐시에 남아 있을 가능성이 높은 블록부터 다시 쓴다.

검증: 4096블록을 다 받을 때까지 할당 → 중복 없음, 범위 안, 정확히 4096개 뒤 `nullptr` → 무작위 순서로 반납,
50라운드 반복해 오류 0.
측정(맥 M2, `-O2`, 같은 할당/반납 패턴 2천만 번, 두 번 실행): 풀 2.1~2.4 ns, `new`/`delete` 119~140 ns.
두 번 실행한 값일 뿐이고, 시스템 할당기 쪽이 왜 이만큼 느린지는 따로 재지 않았다(원인 미확인). 보장되는 건
"풀은 포인터 두 번 옮기기"라는 구조뿐이다.

## 틀 (외워 둘 것)

```python
# 크기 제각각: 빈 조각을 주소 순으로
alloc(size): 앞에서부터 size 이상인 첫 조각 → 앞부분을 주고 나머지를 남김 (딱 맞으면 조각 삭제)
free(addr, size): 주소 순 자리에 끼우고 → 뒤 조각과 붙어 있으면 합치고 → 앞 조각과 붙어 있으면 합친다
```

```cpp
// 같은 크기: 빈 블록 안에 next를 적는다
struct FreeNode { FreeNode* next; };
void* alloc() { if (!head) return nullptr; auto n = head; head = n->next; return n; }
void free(void* p) { auto n = (FreeNode*)p; n->next = head; head = n; }
```

조각 고르는 법: first-fit(처음 맞는 것, 빠름), best-fit(가장 딱 맞는 것, 작은 찌꺼기가 많이 생김), 크기별 목록
(segregated / buddy: 크기를 2의 거듭제곱으로 맞춰 쪼개고 합치기 쉽게).

## 자주 하는 실수

- **병합을 한쪽만**: 뒤만 합치고 앞을 안 합치면 조각이 계속 잘게 남는다. 양쪽 다.
- **병합 순서**: 뒤를 먼저 합치고 앞을 합쳐야 인덱스가 안 꼬인다(예제의 순서).
- **딱 맞는 조각을 크기 0 조각으로 남기기**: 목록에 0짜리가 쌓인다. 지운다.
- **이중 반납 / 모르는 주소 반납**: 목록이 깨지거나 같은 블록을 두 번 나눠 준다. 예제 1은 이름표로 막았다(실제 할당기는 헤더의 표시나 디버그 모드로 잡는다).
- **블록이 포인터보다 작은 intrusive 목록**: `next`를 적을 자리가 없다. 최소 크기를 포인터 크기로.
- **정렬(alignment)**: 실제 할당기는 주소를 8/16바이트에 맞춰야 한다. 예제는 칸 단위라 생략했다.

## 복잡도

예제 1 할당 O(조각 수), 반납 O(조각 수)(파이썬 리스트 삽입) / O(log 조각 수)(C++ `std::map`).
예제 2 할당·반납 O(1).

## 서빙 시스템과의 연결

- **vLLM KV 캐시 = 같은 크기 블록 풀**: KV를 토큰 16개 같은 고정 크기 블록으로 나눠 free list에서 나눠 준다(PagedAttention). 크기가 하나라서 외부 단편화가 없고, 낭비는 마지막 블록의 빈 자리뿐이다. 예제 1의 "합계는 충분한데 연속이 없다"가 바로 이전 시스템들이 겪던 문제다. vLLM의 `FreeKVCacheBlockQueue`는 여기에 LRU 순서(13번)까지 얹은 것이다.
- **PyTorch CUDA 캐싱 할당기**: `cudaMalloc`이 느려서 반납된 GPU 메모리를 바로 돌려주지 않고 크기별 목록에 들고 있다가 다시 나눠 준다. 큰 조각을 쪼개고 합치는 것도 예제 1과 같은 발상이다. "메모리는 남는데 OOM"이 나는 게 외부 단편화다.
- **칩 런타임의 장치 메모리 관리**: NPU 런타임도 장치 메모리를 한 번 크게 잡고 안에서 나눠 주는 할당기가 필요하다(층별 공부 ⑪ 런타임).
- **커널 slab**: 같은 크기 객체(inode 등)를 예제 2처럼 관리한다.
