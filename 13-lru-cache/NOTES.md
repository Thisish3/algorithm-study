# LRU 캐시

## 한 줄 요약

꽉 차면 **가장 오래 안 쓴 것**을 버리는 캐시. `get`, `put` 모두 O(1)이어야 한다. 정답은 하나다:
**해시(키 → 노드) + 이중 연결 리스트(사용 순서)**. System SW 면접에서 직접 짜 보라고 가장 자주 나오는 문제다.

## 왜 둘을 같이 쓰나

| 필요한 일 | 해시만 | 리스트만 | 둘 다 |
|---|---|---|---|
| 키로 찾기 | O(1) | O(n) | O(1) (해시) |
| 사용 순서 갱신 (중간에서 떼어 맨 뒤로) | 순서 없음 | O(1) (노드를 알면) | O(1) (해시가 노드를 알려 줌) |
| 가장 오래된 것 버리기 | ? | O(1) (머리) | O(1) |

해시가 노드 위치를 알려 주고, 리스트가 순서를 지킨다. 이중(prev·next) 연결이라 중간 노드를 O(1)에 뗀다.

## 예제 (`lru_cache`)

용량 2: put 1, put 2, get 1(→10, 1이 최근), put 3(가장 오래된 2를 버림), get 2(→-1), get 3(→30),
put 1=11, get 1(→11), get 3(→30). 적중률 4/5 = 80 %.

검증: 무작위 300개 명령열에서, 리스트를 통째로 뒤지는 O(n) 단순 구현과 **매 연산의 결과**를 비교했고,
Python과 C++ 출력도 비교했다. 모두 같았다. (C++ 쪽이 `get`이 없는 입력에서 빈 줄을 안 찍는 형식 차이를 이
비교로 발견해 고쳤다.)

## 틀 (외워 둘 것)

```python
# 경계용 빈 노드(head, tail)를 두면 "리스트가 비었나" 분기가 사라진다
def _unlink(n): n.prev.next, n.next.prev = n.next, n.prev
def _append(n):                       # tail 바로 앞 = 가장 최근
    n.prev, n.next = tail.prev, tail
    tail.prev.next = n; tail.prev = n
get: 없으면 -1 / 있으면 unlink → append → 값
put: 있으면 값 갱신 + unlink → append / 없고 꽉 찼으면 head.next를 unlink + map에서 삭제 → 새 노드 append
```

```cpp
std::list<std::pair<int,int>> order;                       // 앞 = 최근
std::unordered_map<int, std::list<std::pair<int,int>>::iterator> pos;
order.splice(order.begin(), order, pos[k]);                // 노드를 맨 앞으로 O(1), 반복자 그대로 유효
```

파이썬은 `collections.OrderedDict`의 `move_to_end`, `popitem(last=False)`로 몇 줄이면 되지만, 면접에서는
보통 "직접 연결 리스트로" 짜라고 한다. 둘 다 할 수 있어야 한다.

## 자주 하는 실수

- **버릴 때 해시에서 지우지 않기**: 리스트에서는 빠졌는데 해시가 옛 노드를 가리킨다. 노드에 키를 같이 저장하는 이유.
- **이미 있는 키를 put할 때 용량 검사부터 하기**: 갱신은 개수가 안 늘어나므로 버리면 안 된다. 있는지부터 본다.
- **get에서 순서 갱신을 빠뜨리기**: 읽기도 "사용"이다.
- **용량 0**: put이 아무것도 안 해야 한다.
- **C++에서 `erase` 후 반복자 사용**: `splice`를 쓰면 노드를 지우지 않고 옮기므로 해시의 반복자가 유효하다.
- **경계 노드 없이 짜기**: 머리·꼬리가 빈 경우 분기가 늘어 실수가 생긴다.

## 복잡도

`get`, `put` O(1). 메모리 O(용량).

## 서빙 시스템과의 연결

- **vLLM KV 블록**: 쓰다가 반납된 블록은 prefix 캐시로 남아 있다가, 새 블록이 필요하면 **가장 오래 안 쓴 것부터** 다시 쓴다. vLLM의 `FreeKVCacheBlockQueue`가 바로 이중 연결 리스트이고, 주석에 "중간 블록을 O(1)에 떼려고 deque 대신 직접 만들었다"고 적혀 있다(파이썬 객체 할당도 피하려고 블록의 prev/next 필드를 직접 쓴다).
- **prefix 캐시 적중률**: 이 예제의 적중률이 곧 캐시 성능 지표다. 에이전트처럼 같은 앞부분을 반복하는 부하에서 용량과 적중률의 관계를 이 시뮬레이터로 미리 볼 수 있다.
- **라우터의 근사 캐시 색인**: llm-d처럼 엔진 캐시를 추정하는 쪽도 용량을 정해 두고 오래된 항목을 버린다.
- LRU의 약점: 한 번 훑고 마는 대량 요청이 자주 쓰는 항목을 몰아낸다. 그래서 LFU, 2Q, ARC 같은 변형이 있다.
