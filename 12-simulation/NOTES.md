# 구현 · 시뮬레이션

## 한 줄 요약

새 알고리즘이 필요 없고, **문제의 규칙을 빠짐없이, 순서대로** 코드로 옮기는 문제. 틀리는 이유는 거의 다
"규칙 하나를 빠뜨림", "순서가 바뀜", "경계 조건"이다. 코딩 테스트에서 가장 자주 나오고 가장 시간을 많이 쓴다.

## 예제: KV 블록 할당과 선점 스케줄러 (`kv_scheduler`)

vLLM 스케줄러를 단순화했다. GPU에 KV 블록 B개, 블록 하나에 토큰 S개. 스텝마다 **도착 → 받기 → 생성 → 완료**
순서로 진행하고, 생성 중 새 블록이 필요한데 없으면 **가장 나중에 받은 요청을 선점**한다(블록 반납, 만든 토큰을
버리고 대기열 맨 앞으로 = vLLM v1의 재계산 선점). 규칙 전문은 `kv_scheduler.py` 맨 위에 있다.

예제 입력(블록 6개, 블록당 4토큰, 요청 4개)의 답은 완료 스텝 `4 5 8 7`, 선점 1번이다. 스텝 2에서 요청 0이
세 번째 블록을 원하는데 남은 블록이 없어서, 가장 나중에 받은 요청 2가 선점된다.

### 검증하는 법: 정답을 구하기 어려울 때

이런 문제는 "모든 경우를 다 보는" 정답 코드가 따로 없다. 그래서 두 가지를 했다.

- **두 구현 비교(차분 테스트)**: 같은 규칙을 Python과 C++로 따로 짜고, 무작위 입력 300개에서 결과가 같은지 비교했다. 한쪽에만 있는 실수(규칙을 다르게 읽음)를 잡는다. 300개 모두 같았다(선점은 모두 합쳐 599번 발생해서 선점 경로도 충분히 지나갔다).
- **불변식 확인**: 매 스텝 "남은 블록 + 요청들이 가진 블록 = 전체"를 `assert`로 확인했다. 블록을 두 번 반납하거나 안 돌려주는 실수를 잡는다.

손으로 예제를 한 스텝씩 따라가 보는 것도 꼭 한다(위 예제도 손으로 맞춰 봤다).

## 구현 문제 푸는 순서

1. **규칙을 번호 매겨 옮겨 적는다.** 문제의 문장 하나 = 코드 블록 하나가 되게. 예제의 1~4번 주석이 그것.
2. **상태를 정한다.** 무엇을 들고 다니나(대기열, 실행 목록, 요청별 진행, 남은 블록). 이름을 문제의 용어로.
3. **한 스텝 함수를 짠다.** 순서가 바뀌면 답이 바뀐다(받기 → 생성 순서를 바꾸면 결과가 달라진다).
4. **예제를 손으로 따라가며 상태를 출력해 본다.**
5. **경계**: 같은 시각 도착, 빈 목록, 자기 자신이 선점되는 경우, 끝나지 않는 입력.

## 자주 하는 실수

- **목록을 돌면서 그 목록을 수정**: 예제처럼 복사본(`list(running)`)을 돌고, 원본에 아직 있는지 확인한다.
- **순서 규칙 놓치기**: "같은 스텝이면 번호 순", "맨 앞이 안 되면 뒤도 안 받음(FIFO)" 같은 문장.
- **2차원 격자 방향**: `dr = [-1, 0, 1, 0]; dc = [0, 1, 0, -1]`로 고정하고 회전은 `(d + 1) % 4`.
- **격자 회전**: 시계 방향 90도는 `new[c][n-1-r] = old[r][c]`. 작은 예로 확인하고 쓴다.
- **시간을 한 칸씩 돌리는데 너무 느림**: 아무 일도 없는 구간은 다음 사건 시각으로 건너뛴다(04번 힙 예제의 "놀고 있으면 다음 도착으로").
- **끝나지 않는 입력**: 예제는 스텝 상한을 두고 멈춘다. 블록이 요청 하나도 못 담을 만큼 적으면 영원히 돈다.

## 서빙 시스템과의 연결

- 이 예제 자체가 엔진 스케줄러의 축소판이다(층별 공부 ⑥: 연속 배칭, PagedAttention 블록, 선점).
- 실제 시스템을 설계할 때도 이런 작은 시뮬레이터로 규칙을 먼저 확인한다. 층별 ⑤의 라우팅 시뮬레이션, ⑥의 배칭 비교, ttalkkak 자동 증감 판단 함수 테스트가 모두 같은 방식이다.
- 두 구현을 비교하는 검증은 차분 테스트(Dynamo·llm-d 파서 버그를 찾은 방법)와 같은 발상이다.
